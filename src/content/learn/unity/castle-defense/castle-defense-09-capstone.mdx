Press Play and watch every chapter fire at once. Zombies spawn (coroutine), path to the
gate (NavMesh), blending idle-to-run as they go (agent→animator bridge, blend tree).
The hero casts on a timer (interface), her clip fires an Animation Event (particles),
damage lands (health, triggers, hit VFX), deaths bubble up as events, waves clear, the
retargeted boss arrives, and the sequencer coroutine walks the phases to `Victory`.

## The map of everything

<CycleDiagram steps="CapstoneSequencer|coroutine spawns wave,ZombieSpawner|instantiates + wires,NavMesh + Animator|zombies path and animate,Hero + VFX|casts damage via events,ZombieHealth|onDeath bubbles up,onWaveCleared|resumes the sequencer" note="one full lap = one wave; the boss is the same lap with one prefab swapped" />

Every arrow in that loop is a seam you studied:

| Seam | Chapter | The contract |
|------|---------|--------------|
| Bake scoped to a proxy layer | 1 | `NavMeshSurface.layerMask` |
| Pathfinding → animation | 2 | `agent.velocity` → `Speed` float |
| Parameters → states | 3 | Animator conditions, Any State triggers |
| Clips across rigs | 4 | Humanoid muscle retargeting |
| Moments → VFX | 5 | `VfxEmitter.Play()` from code or Animation Event |
| Input → combat | 6 | `IHeroInputSource.RequestCast()` |
| Systems → sequencing | 7 | `UnityEvent` up, `WaitUntil` across |
| Data → behaviour | 8 | `CastleDefenseConfig` asset |

The architecture rule underneath all of it: **no monolith**. `ZombieSpawner`,
`HeroCombatController`, and `CapstoneSequencer` are separate, independently swappable
components. The sequencer never touches Animator, VFX, or NavMesh. Input is an
interface. That's why the roadmap — player-controlled heroes, multiple heroes on the
wall, deployable defender bots — is additive work, not a rewrite.

## Break it on purpose — cross-system edition

Each break shows up as a symptom in a *different* system than the one you broke.
Diagnose from the symptom before you "know" the cause; that's the actual skill.

1. **Break the bridge:** in the Animator window, raise Idle → Chase's condition to
   `Speed > 999`. Symptom: statues gliding to the gate. Movement is NavMesh; the pose
   is Animator; the bridge between them is one condition.
2. **Break the event chain:** comment out `onWaveCleared.Invoke()` in
   `ZombieSpawner.cs`. Symptom: wave 1 dies, phase text stays `Wave1` forever. Nothing
   crashed — an event that never fires looks exactly like a game that's "thinking."
3. **Break the impact:** remove the `OnCastImpact` Animation Event from the cast clip
   *and* set `impactFallbackDelay` to 999. Symptom: the hero animates beautifully,
   zombies never take damage, and eventually a wave stands at the gate unkillable —
   the exact bug this package shipped with and fixed.

Rebuild with Step 2 (and revert code edits) after each.

## Interview corner

**Q: Walk me through debugging "enemies stopped reaching the objective" in a system
like this.**
A: Bisect by seam. Do agents have a path (`agent.hasPath`, NavMesh overlay visible)?
If no — bake/placement problem. If yes, are they moving (`agent.velocity`)? If no —
avoidance/radius/priority deadlock or `isStopped`. If they arrive but nothing happens —
range checks, event wiring, or the kill path. Each seam has an observable, so check
observables in order instead of guessing.

**Q: Why avoid a central GameManager, and what replaces it?**
A: A monolith accretes every system's knowledge and becomes the file everyone edits and
merge-conflicts on. Replace it with small components owning one concern each, decoupled
by events/interfaces, plus — if needed — one *thin* sequencer that coordinates timing
but holds no domain logic. This package's `CapstoneSequencer` is that pattern.
